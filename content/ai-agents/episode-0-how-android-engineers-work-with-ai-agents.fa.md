این متن، نسخهٔ نوشتاری **Episode 0** است. مقاله را برای استدلال کامل بخوان؛ ویدیو را برای روایت شفاهی ببین. یک ایده، دو رسانه.

## سؤال واقعی

این سری برای برنامه‌نویس‌های اندروید است.

نه برای کسانی که می‌خواهند با یک جملهٔ انگلیسی و بدون مبانی، کلون فروشگاه بسازند.

اگر با Agent کد اندروید نوشته‌ای — گاهی عالی بوده و گاهی دو روز بعد نصف پروژه را دلت می‌خواسته دور بریزی — این برای توست.

دیگر بحث نمی‌کنیم «آیا باید از AI استفاده کرد؟»  
آن بحث تمام شده.

سؤال مفید ساده‌تر و سخت‌تر است:

**چطور به Agent brief می‌دهی؟**

## این قسمت چه به تو می‌دهد

تا آخر این پنج چیز را داشته باش:

1. نقشهٔ چهار روش واقعی کار تیم‌ها با Agent  
2. مدل هزینهٔ صادقانه: توکن، بازکاری، ریسک دستگاه  
3. چرا کار spec-driven معمولاً برای اپ واقعی ارزان‌تر است  
4. Spec بد روی اندروید چه چیزهایی را بی‌سروصدا خراب می‌کند  
5. قدم بعد این سری — زاویهٔ محصول واقعی با قیود اندروید (آفلاین، متن‌بازمحور، verify روی دستگاه)

نه دموی habit tracker. نه کلون اینستاگرام.

## جابه‌جایی

چند سال پیش سؤال‌های اصلی این‌ها بود: Kotlin بلدی؟ Compose بلدی؟ معماری‌ات feature دوم را دوام می‌آورد؟

حالا یک لایهٔ جدید هست: Agent. می‌تواند فایل بسازد، ریپو را بخواند، تست پیشنهاد بدهد، و چند دقیقه بدون تایپ خط‌به‌خط تو کار کند.

حقیقت سخت:

**Agent سرعت را چندبرابر می‌کند. قضاوت مهندسی را جایگزین نمی‌کند.**

روی اندروید این مهم‌تر از یک دموی وب دورریختنی است.

بیلد سبز Gradle موفقیت نیست. هنوز lifecycle، تغییر پیکربندی، مجوزها، محدودیت بک‌گراند، ذخیره‌سازی آفلاین، لبه‌های ناوبری، و رفتار روی گوشی ارزان با دیسک کند مال توست.

پس نپرس «AI استفاده می‌کنی؟»  
بپرس: **وقتی با Agent حرف می‌زنی، کدام روش را داری؟**

## چهار روش واقعی تیم‌ها

در کار واقعی این‌ها قاطی می‌شوند. برای تصمیم‌گیری جدا نگهشان دار. اگر نتوانی نام حالت را بگویی، احتمالاً تصادفی vibe می‌کنی.

### ۱) Hand-coding

خودت می‌نویسی. AI حداکثر یک autocomplete قوی است.

**قوت:** کنترل کامل و فهم عمیق. هنوز برای مسیرهای امنیتی، همزمانی سخت، یا جایی که abstraction غلط یک سال درد می‌سازد درست است.

**هزینه:** اگر در محصول بزرگ هر صفحه و هر repository را دستی بنویسی، به تیم‌هایی که خوب brief می‌کنند می‌بازی.

Hand-coding نمرده؛ فقط دیگر تنها حالت حرفه‌ای نیست.

### ۲) Copilot / assistive

هنوز تو راننده‌ای. Agent یک تابع، یک متد ViewModel، یک پچ کوچک پیشنهاد می‌دهد. قبل از Accept می‌فهمی چه عوض شده.

**قوت:** حالت روزمرهٔ سالم برای مهندس باتجربه. معماری در سرت می‌ماند؛ مدل فقط ضریب است.

**هزینه:** اگر از خستگی Accept بزنی، بدهی vibe از در پشتی می‌آید. Assistive وقتی review نباشد بی‌سروصدا می‌میرد.

**قاعده:** اگر diff را توضیح نمی‌دهی، نگهش ندار.

### ۳) Vibe coding

با زبان طبیعی یک حس را توصیف می‌کنی. مرز محصول سخت نیست. معیار پذیرش تیز نیست. بیشتر امید می‌ورزی تا هدایت.

**قوت:** عالی برای spike. شاید در یک ساعت چیزی روی emulator ببینی. برای شکل API خوب است.

**هزینه:** روی اندروید بعداً گران می‌شود. مجوز نصفه. state عجیب. ناوبری چسبی. ذخیره‌سازی با content URI که بعد از reboot می‌میرد. Feature دوم می‌آید و Agent در درهمی که با رضایت تو ساخته گم می‌شود.

Vibe coding شیطانی نیست.  
اشتباه گرفتنش با محصول قابل‌نگهداری هست.

**Vibe برای کشف است. تحویل جدی معمولاً بیشتر لازم دارد.**

### ۴) Spec-driven

قبل از کد Agent، تو تصمیم‌ها را می‌نویسی:

- چه می‌سازیم و چه را رد می‌کنیم  
- قوانین پروژه‌ای که بین sessionها نلغزند  
- رفتار دقیق فیچر با empty state و خطا  
- چطور روی دستگاه واقعی موفقیت را verify می‌کنی  

بعد Agent پیاده می‌کند. بعد تو verify می‌کنی: compile، run، مسیر پذیرش، در صورت نیاز review دوم.

**قوت:** کنترل + سرعت پایدار. کمتر فراموشی context بین چت‌ها. کمتر آخر هفتهٔ «نصف اپ را بازنویسی کن».

**هزینه:** اول باید فکر کنی و بنویسی. ده دقیقه Spec متمرکز اغلب ساعت‌ها بازنویسی و توکن سوخته می‌خرد.

اگر review چندایجنتی می‌خواهی، زیر همین چتر بمان. یکی می‌سازد؛ یکی review می‌کند. این هنوز انضباط است — نه دین جدید.

## مدل هزینه (این را یادت بماند)

| حالت | کنترل | سرعت اول | ریسک بعد |
|------|--------|----------|----------|
| Hand-coding | بالا | کم | کم (اگر تمام کنی) |
| Copilot | بالا | متوسط | کم اگر review کنی |
| Vibe | کم | انفجاری | روی اندروید انفجاری |
| Spec-driven | بالا | متوسط بعد از brief | برای اپ واقعی کمترین |

قاعدهٔ طلایی اندروید: اگر فیچر از UI ساده فراتر است — ذخیره، نوتیف، مجوز، ناوبری، یا چند لایه — تنها با vibe نرو.

**پرامپت ارزان، اشتباه گران است.**

## فایل‌های harness (کوتاه)

اسم‌هایی مثل README، CLAUDE، AGENTS، SKILL و پوشهٔ `specs` را دیده‌ای. همه Markdownاند. اسم فایل مخاطب را مشخص می‌کند.

- **README** — برای انسان  
- **AGENTS.md / CLAUDE.md** — قوانین سراسری پروژه برای هر session  
- **SKILL** — رویهٔ یک کار؛ فقط وقتی آن کار هست  
- **specs** — رفتار محصول، صفحه، edge case، غیرهدف‌ها  

قاعدهٔ ساده:

- قانون کل پروژه → AGENTS / CLAUDE  
- رویهٔ یک شغل → SKILL  
- آنچه محصول باید بکند → specs  

## Spec بد روی اندروید

اینجا هنوز قضاوت سینیور اندروید نان درمی‌آورد.

پرامپت مبهم مثل «یک اپ سلامت قشنگ بساز» می‌تواند UI Compose زیبایی بدهد که برای واقعیت غلط است. شکست‌هایی که با brief نرم دیده‌ام:

- UI فرض شبکه دارد در حالی که محصول آفلاین وعده داده  
- اپ به‌جای کپی بایت‌ها به storage خصوصی، gallery content URI نگه می‌دارد — بعد مدرک غیب می‌شود  
- مانیفست بی‌دلیل INTERNET می‌گیرد — برای اعتماد و مسیر F-Droid خطرناک  
- متن شبیه تشخیص پزشکی می‌شود  
- معماری برای یک صفحه کار می‌کند و با پوشه و Prep و Settings می‌ترکد  

Agent تصادفی به تو خیانت نکرد.  
تو دنیایی را که اپ باید در آن زنده بماند کم‌مشخص کردی.

## چطور brief کنیم (چهار لایه)

لوگوی ابزار فرعی است. این حلقه را بگیر:

1. **قصد محصول** — چه می‌سازیم، چه را رد می‌کنیم (مثال: قفسهٔ آفلاین مدارک مراقبت + چک‌لیست Prep؛ بدون اکانت اجباری؛ بدون کلود؛ بدون ادعای تشخیص)  
2. **قانون اساسی پروژه** — Kotlin، Compose، دادهٔ local-first، وابستگی‌های دوست‌دار FOSS، مرز لایه‌ها، بدون business logic داخل Composable  
3. **Spec فیچر** — اقدام کاربر، پاسخ سیستم، empty state، خطا، معیار Done روی سخت‌افزار. کوتاه. دقیق. نه رمان.  
4. **حلقهٔ verify** — بیلد، اجرا، مسیر پذیرش، اصلاح. در صورت نیاز pass دوم. تو ناظر هستی. Blind Accept یعنی vibe با کت‌وشلوار.  

Gemini، Claude، Cursor، Agent استودیو — همان حلقه.  
مدل قوی‌تر بدون Spec فقط سریع‌تر شکست می‌خورد.

## این سری بعداً چه می‌سازد

وسیلهٔ سری: آرشیو آرام و آفلاین مدارک مراقبت؛ پوشه‌های ساده (آزمایش، نسخه، بیمه)؛ چک‌لیست Prep قبل مراجعه؛ مسیر FOSS به‌سوی F-Droid.

نه habit tracker. نه شبکهٔ اجتماعی. نه مارکت‌پلیس کلینیک.

Spec را علنی می‌نویسیم، بعد زیر همان قرارداد با Agent پیاده می‌کنیم — و روی دستگاه واقعی verify می‌کنیم.

## چهار تصویر را نگه دار

1. Hand-coding — وقتی باید هسته را کامل مال خودت کنی  
2. Copilot — سرعت کنترل‌شده روی ویرایش کوچک  
3. Vibe — کشف، نه تحویل جدی  
4. Spec-driven — پیش‌فرض اپ واقعی  

Agent آمده مهندس اندروید را عوض کند؟ نه.  
آمده تصمیم‌هایت را سریع‌تر اجرا کند — اگر تصمیم را بنویسی.

**کد را حدس نزن. هدایتش کن.**
